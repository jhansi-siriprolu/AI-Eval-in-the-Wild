Log-likelihood scoring vs. generate_until

How MMLU, HellaSwag & ARC score answers without ever writing one — and why that's what lets them run on an 8GB laptop while GSM8K-style generation can eat all your RAM.

0Glossary — the abbreviations you'll see everywhere

Every term below also shows a tooltip if you hover over it later on this page (dotted underline). Skim this once before continuing — the rest of the lesson leans on all six.

⟨bos⟩ / BOSBeginning of sequence — a special token the tokenizer inserts before your actual text so the model has "something" to condition on for the very first real word. It isn't a word you typed; it's a fixed marker every prompt starts with, the same way a sentence starts with a capital letter. When you see log P(answer | ⟨bos⟩), read it as "the probability of 'answer' being the very first word, right after this synthetic start marker."
logitThe model's raw, unnormalized "score" for one candidate word — can be any real number (negative, zero, huge). On its own a logit isn't a probability; it only becomes one after softmax below. Bigger logit = model wants that word more, but "wants it more" only means something relative to the other logits it's being compared against.
softmaxThe formula that turns a list of logits into real probabilities: exponentiate each one, then divide by the sum of all the exponentials. This is why softmax is a competition, not an independent measurement — raising one word's logit doesn't just help that word, it also divides the probability pie into different-sized slices for every other word, because they all have to add up to 1.
log-likelihoodInstead of multiplying several probabilities together (each <1, so the product keeps shrinking and can underflow to 0 on a computer), take the log of each probability first and add them. Same ranking, safer arithmetic. A log-probability is always ≤ 0 (0 = "certain", very negative = "very surprised").
argmax"Pick whichever option has the biggest value." argmax over logits, probabilities, or log-probabilities all give the same winner for a single token, because log and softmax are both order-preserving — they stretch or compress the gaps between numbers but never reorder them.
KV cacheKey/Value cache — every generated token, once produced, has its internal "Key" and "Value" attention vectors saved so the model doesn't have to recompute them when it looks back at that token later. It's the main thing eating your RAM during long generation (Section 5).

1The one function underneath everything

A language model is, mechanically, a function you can call over and over: feed it some tokens (the "context"), it hands back one score — a logit — for every word in its vocabulary, saying how much it "wants" to produce that word next.

P(next = v | context) = softmax(logits)v

Softmax just rescales the raw logits into numbers between 0 and 1 that add up to 1 — a genuine probability distribution. Every benchmark below is just a different way of calling this same function, over and over, and doing different arithmetic with the results.

Try it: a tiny hand-built model is asked what word comes next after "the capital of france is ___". It has already assigned a logit to every candidate word in its vocabulary — you are not changing the sentence or the words themselves, only one number: how strongly the model favors "paris".

Only paris's logit moves (you drag this). berlin, rome, madrid, and a keep the exact same logits the whole time (fixed: 3.0 / 2.5 / 0.5 / 1.0). Watch their bars shrink or grow anyway — that's the point. Softmax forces every probability in the row to add up to 1, so the moment "paris" gets more confident, it isn't just gaining — it's taking probability mass away from the other four, who had no say in it. Nothing is being reordered or jumbled; one dial turns, and the shared 100% gets redivided.

Try dragging to 0: "paris" now has the lowest logit of the five, so it loses the "winner" highlight to whichever fixed word has the next-highest logit — proof the other bars were never frozen, only their logits were.

2loglikelihood: scoring a string you already have

MMLU, HellaSwag, and ARC are all multiple choice. The harness never asks the model to write anything — it already has the candidate answers as literal strings. So instead of generating, it asks a narrower question per choice: "if I forced you to say exactly this, how surprised would you be?"

score(c) = Σᵢ log P(cᵢ | context, c₁, ..., cᵢ₋₁)

Sum of log-probabilities across the tokens of the candidate continuation. Two reasons for logs, not raw probabilities:

  • Numerical stability — multiplying many numbers < 1 underflows to 0 in floating point; adding their logs doesn't.
  • Additive reasoning — each token's contribution is a separate, inspectable term, which is exactly what the trace below shows.

Worked trace — scoring the continuation "answer : 7" token by token:

Reading the notation: log P(x | y) means "the log-probability of token x, given that everything to the right of the | came before it." ⟨bos⟩ is not a real word — it's the fixed "start of input" marker every prompt begins with (see the glossary), so step 1 reads as "how likely is 'answer' to be the very first word, right after the sequence begins."

step 1  log P(answer | ⟨bos⟩)  =  -5.144  (P = 0.006 — rare to start a sentence this way)
step 2  log P(: | ⟨bos⟩ answer)  =  -0.021  (P = 0.980 — "answer" is almost always followed by ":")
step 3  log P(7 | ⟨bos⟩ answer :)  =  -0.840  (P = 0.432 — model's best guess for the number)
total log-likelihood = -5.144 + -0.021 + -0.840 = -6.005

Compare against "answer : 42": same first two steps (identical context up to there), but step 3 scores -2.340 instead — so its total is -7.505, lower (worse). "7" wins.

Notice steps 1 and 2 are identical between the two candidates — the shared prefix only needs to be computed once. Real eval harnesses exploit exactly this to score many choices efficiently.

Why does the model sometimes pick the answer with the lower bar?

It never does for single-token answers — probability and log-probability rank identically since log is monotonic. But once continuations differ in length or in multiple tokens, you're comparing sums of several log-probs, and a short confident answer can beat a long, hesitant one even if a naive "look at the first token" comparison suggests otherwise. Try the math question above and lengthen one option conceptually by imagining a 2-token wrong answer like "twelve" (two tokens in a real tokenizer) against a 1-token right answer — the extra token is one more chance to lose probability mass.

4generate_until: producing a string you don't have yet

GSM8K wants free-form reasoning: "Natalia sold clips to 48 friends in April, then half as many in May. How many total?" There's no fixed list of candidates to score. The model must generate, one token at a time:

loop until stop_string appears in output, or max_tokens reached:
    1. forward pass on (context + everything generated so far)
    2. pick next token (argmax, or sample from the distribution)
    3. append it — now the context is one token longer
    4. check: does the output so far contain a stop string?

The key difference from Section 2: every loop iteration is a full forward pass, and each one depends on the output of the previous one — they cannot be parallelized. A 60-token chain-of-thought answer costs 60 sequential forward passes (with a KV cache reused across them — see next section) versus loglikelihood's fixed, known-length pass per candidate.

5The KV cache: where the memory actually goes

Both scoring and generation are "just forward passes" — so why does one comfortably fit 8GB and the other can blow past it? The answer is the KV cache. Every transformer layer's attention needs the Key and Value vectors of every token seen so far. Recomputing those from scratch at each new generated token would be enormously wasteful, so inference engines cache them — and that cache grows with sequence length.

KV cache bytes = 2 × layers × heads × head_dim × seq_len × batch × dtype_bytes
SymbolMeaningTypical 7B-class value
layers (L)transformer blocks stacked32
heads (H)attention heads per layer32
head_dimdimension per head128
seq_len (S)tokens processed so far — grows every generation stepvaries!
batch (B)examples scored/generated togethervaries
dtype_bytes2 for fp16/bf162
The variable that changes everything: S. loglikelihood scoring has a short, known-in-advance S (question + one answer choice). Free-form generation has an open-ended S that you only discover by running — a model that rambles for 500 tokens before hitting its stop string pays for 500 tokens of KV cache, and if you're generating a whole batch at once, that cost multiplies by batch size too.
